## 01 HTTP 演进

> [!abstract] 一句话
> HTTP 每一代都在治 **队头阻塞（Head-of-Line Blocking, HOL）**，只是治的层级不同。

### HTTP/1.1 —— 应用层队头阻塞
- **痛点**：同一条 TCP 连接上，前一个请求的响应没回来完，下一个请求发不出去。一个慢请求堵死后面所有请求。
- **打补丁**：浏览器给同域名开 6 条并发 TCP 连接（治标不治本，连接建立/维护开销大）。

### HTTP/2 —— 多路复用治好应用层 HOL，却引入 TCP 层 HOL
- **二进制分帧 + 多路复用**：一条 TCP 连接里，多个流（stream）切成帧（frame）交错传输，互不堵塞。连接数从 6 降到 1。
- **HPACK**：头部压缩，不再重复发 Cookie 那一堆。
- **Server Push**：服务器主动推资源（基本已废弃，不用记）。

> [!warning] ⚠️ HTTP/2 的遗留坑：TCP 层队头阻塞
> 所有流共跑 **一条 TCP 连接**。TCP 强制 **字节按序交付** —— 一个包丢了，TCP 卡住等重传，**后面已到达的、属于其他流的数据也不交给上层**。
> 结果：一个丢包堵死整条连接上的所有流。HTTP/2 在应用层解耦了流，TCP 又把它们在传输层重新绑在一起。

### HTTP/3 —— 换掉 TCP，用 QUIC
- 基于 **UDP** 的 **QUIC** 协议，在 UDP 之上自己实现可靠传输（重传/拥塞控制）。
- **流独立可靠**：每个流自己排序、自己重传，丢包只影响该流，不跨流。
- 把"传输层握手 + TLS 加密握手"**合并** → 省 RTT。
- **连接迁移**：IP 变了（Wi-Fi 切 4G）连接不断，移动端友好。

> [!tip] 面试速记
> **1.1** 应用层 HOL（多开连接硬扛）→ **2** 多路复用治好应用层 HOL，却因共跑一条 TCP 引入 **TCP 层 HOL** → **3** 换 QUIC(UDP)，流独立可靠，根治。

## 02 HTTPS 与 TLS 握手

> [!abstract] 一句话
> HTTPS = HTTP + TLS。**混合加密**：非对称商量会话密钥，对称传数据。

### 为什么必须混合加密

|  | 对称加密 | 非对称加密 |
|---|---|---|
| 用什么密钥 | 双方同一个 | 公钥加密 / 私钥解密 |
| 速度 | 极快 | 慢 100～1000 倍 |
| 各自难处 | 密钥怎么安全传过去 | 太慢，传不了网页 |

> [!note] 解法
> 先用 **非对称** 加密安全商量出一个对称的"会话密钥"，之后所有数据用 **对称** 加密。非对称解决"密钥传递"，对称解决"传输性能"。

### 数字证书的作用

> [!warning] 常见误区：证书不是用来加密数据的！
> 证书验的是 **身份** —— 证明"这个公钥确实属于这家服务器"，防冒充。
> 浏览器用内置的 CA（公证处）公钥去验证书上的签名，验得过才信。

### TLS 1.2 完整握手（2 个 RTT）

```
Client ── ClientHello ──────────────────> Server   (算法列表 + 随机数A)
Client <── ServerHello + 证书 + Done ───── Server   (选定算法 + 随机数B + 公钥)
Client ── ClientKeyExchange + Finished ──> Server   (预主密钥，用服务器公钥加密)
Client <── Finished ───────────────────── Server
```

> [!question] 为什么 TLS 1.2 必须要 2 个 RTT？
> 客户端的密钥交换消息 **依赖服务器先发来的证书 / DH 参数**，必须一来一回。
> - RSA 交换：要用服务器公钥加密预主密钥 → 公钥在证书里 → 必须先收证书。
> - DHE 交换：要先拿到服务器的 DH 参数 → 必须先收 ServerKeyExchange。
>
> 所以客户端的密钥素材 **没法跟 ClientHello 一起首发**，多吃一个 RTT。

### TLS 1.3 砍到 1 RTT
- 删掉 RSA、CBC、SHA1 等不安全算法，**只保留 (EC)DHE**。
- 算法空间变小 → 客户端能 **预判** 服务器选哪条曲线 → **密钥素材提前塞进 ClientHello**。
- **安全精简和握手提速是同一件事**：不是为快而减 RTT，而是删不安全算法 → 算法空间小 → 能预判 → 少 RTT。

> [!note] 前向安全性（Forward Secrecy）
> (EC)DHE 每次握手生成 **临时密钥对**，用完就扔。即使服务器私钥泄露，也解不开历史流量。
> RSA 密钥交换做不到（私钥泄露 = 全部历史流量暴露），所以被删。

### 0-RTT（会话恢复）
- 靠 PSK / Session Ticket，客户端第一个包 **直接带加密的应用数据**，连握手 RTT 都省。
- ⚠️ **重放攻击风险**：攻击者可截获 0-RTT 数据原样重播。
- **只能用于幂等请求**（GET），不能用于 POST/转账等。

> [!tip] 面试速记
> HTTPS = HTTP + TLS；混合加密（非对称商量密钥、对称传数据）；证书验身份（不加密）；TLS1.2 = 2 RTT；TLS1.3 删 RSA 只留 (EC)DHE → 1 RTT；0-RTT 靠 PSK 但怕重放，只限幂等。

## 03 TCP 四次挥手与 2MSL

> [!abstract] 一句话
> 挥手要四次是因为 **全双工**；等 2MSL 是 **数学最坏上界**，不是经验值。

### 为什么挥手要四次、握手只要三次
- **握手**：服务器把"同意"和"我也想连"合并成一个包（SYN+ACK）。
- **挥手**：被动方收到 FIN 时往往 **还有数据要发**，所以 ACK 和自己的 FIN **不能合并**，必须分两个包。

### 状态机

```
主动关闭方:  ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
被动关闭方:  ESTABLISHED → CLOSE_WAIT  → LAST_ACK   → CLOSED
```

> [!warning] 服务器怕 CLOSE_WAIT，不是 TIME_WAIT
> TIME_WAIT 出现在 **主动关闭方**。
> 服务器出现大量 **CLOSE_WAIT** = 应用收到对方 FIN 后忘了 `close()`，是 **应用 bug**。

### 为什么 TIME_WAIT 必须等 2MSL —— 两个原因

1. **保证最后的 ACK 能送达**：最后那个 ACK 是主动方发的，丢了的话对方会重发 FIN，主动方必须还活着才能再回一次 ACK。
2. **让本次连接的旧报文消亡**：等够时间，让迷途报文（路由环路、延迟）在网络中死透，不污染下一个复用相同四元组的新连接。

### 2 倍 MSL 是怎么算出来的

```
t=0      客户端发出最后的 ACK（开始等待）
         │   ⚠ 万一这个 ACK 丢了?
t=1 MSL  丢的 ACK 最长飘到这时消亡；服务器没等到 → 超时重发 FIN
         │
t=2 MSL  重发的 FIN 最长再花 1 MSL 飘回客户端
         │   → 客户端若还活着，就能再回一次 ACK
```

> [!tip] 一句话
> **2 MSL = (ACK 最长存活 1) + (重发 FIN 最长传输 1)**，是数学上的最坏上界。
> MSL 的数值（如 30s）是工程经验，但"取 2 倍"是严谨推导。别把两件事搞混。

> [!note] MSL vs TTL vs RTT
> **TTL** = IP 层概念，一个包还能经过几跳路由器（跳数，不是时间）。
> **MSL** = TCP 层概念，报文段最长存活时间。
> **RTT** = 动态测量的往返时延。

## 04 综合验证 RTT 计数

> [!abstract] 经典面试题
> 从浏览器发起到收到首字节，全程要几个 RTT？

### HTTP/1.1 + TLS 1.2 = **4 个 RTT**

```
RTT 1: TCP 握手（SYN → SYN+ACK，最后的 ACK 搭车发 ClientHello）
RTT 2: TLS 1.2 第 1 轮（ServerHello + 证书）
RTT 3: TLS 1.2 第 2 轮（ClientKeyExchange + Finished）
RTT 4: HTTP 请求 → 收到首字节
```

> [!warning] 算 RTT 题的坑
> "从第一个包发出到第一个有效字节回来" **全程都要数**。常错：只数 TLS 握手，漏掉 TCP 握手或 HTTP 往返。

### HTTP/3（QUIC + TLS 1.3）= **2 个 RTT**
- QUIC 把传输层握手和 TLS 握手 **合并** → 1 RTT。
- HTTP 请求 → 首字节 → 1 RTT。
- **0-RTT 恢复**：把请求塞进握手第一个包 → 1 RTT 拿到响应。

> [!question] 为什么 HTTP/3 能省一半？
> ① QUIC 合并传输握手 + TLS 握手；② TLS 1.3 本身只 1 RTT。

## 📌 错因与防坑

> [!danger] 反向提问陷阱
> 看到"下列哪项 **不正确 / 错误 / 除外**"，**第一动作是把题干关键词圈出来**再读选项。
> 否则你会拿着一个 **正确的描述** 当成"错误的那条"选下去。

> [!danger] 2MSL 不是经验值
> "MSL 的数值（30s）" 是工程经验，"取 2 倍" 是数学最坏上界推导。
> 别把"数值是经验"和"倍数是经验"搞混。

> [!danger] 证书不是加密的
> 证书验身份，不加密数据。加密靠密钥协商出来的会话密钥。

> [!danger] UDP ≠ 不可靠
> HTTP/3 用 UDP，但 QUIC 在 UDP 之上自己实现了可靠传输。不是"用 UDP 所以不可靠"。
