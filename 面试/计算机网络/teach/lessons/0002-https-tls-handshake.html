HTTPS 完整握手 & TLS 1.3 为什么砍到 1 RTT

HTTPS = HTTP + TLS。核心一句话:混合加密—— 非对称商量密钥,对称传数据。约 20 分钟。

一、先建直觉:明信片 vs 加密信封

HTTP(明信片)HTTPS(加密信封)
你的请求/响应是明文写在明信片上。每个经手人——路由器、运营商、咖啡店 WiFi、中间黑客—— 都能看,也都能悄悄改(换成假页面、插广告、劫持跳转)。 给明信片套一个只有收件人能拆的加密信封。经手人只能看到"有封信寄给谁", 看不到内容,改一个字收件人也能发现(有完整性校验)。
HTTPS 干两件事:加密(看不到)+ 完整性(改不了)+ 身份认证(不是假的)。 前两个靠 TLS 的密码学,第三个靠数字证书。

二、为什么必须"混合"加密?

这是整堂课的"根问题"。两种加密各有硬伤,谁单独上都崩:

维度 对称加密
(AES)		 非对称加密
(RSA / ECDHE)
密钥 双方同一个密钥 公钥/私钥一对
速度 极快(硬件加速,适合大流量) 慢 100~1000 倍(大数运算)
硬伤 密钥怎么安全传过去?
明文传等于没加密		 太慢,传一个网页
能把 CPU 跑满
🎯 解法(混合加密):
  • 非对称加密只干一件小事——商量出一个会话密钥(对称密钥)。
  • 对称加密用这个密钥,加解密后面所有真实数据。
  • 慢的非对称只用一次(握手),快的对称干重活(传数据)。

三、数字证书:验身份,不是加密数据

⚠️ 最大误区(面试常坑):证书不是用来加密数据的。 证书的作用是证明"这个公钥真的是这个网站的",也就是防冒充。

没有证书会怎样? 你连 taobao.com,黑客中间插一脚,把自己的公钥塞给你, 你还以为这是淘宝的公钥,用它加密 → 黑客用自己私钥解开。这叫中间人攻击(MITM)。

角色在 HTTPS 里的类比
CA(证书颁发机构) 公证处。淘宝把"我是 taobao.com、我的公钥是 XXX"提交给 CA,CA 核验身份后用自己的私钥给这段信息签名,签完的就是证书。
证书 一个经公证处盖章的"身份证 + 公钥"组合。内容是明文,但盖了 CA 的防伪章(签名)。
浏览器内置 CA 公钥 操作系统/浏览器出厂自带一批根 CA 的公钥。这是"信任的起点"——你信的不是网站,是预装的 CA。
验签流程(简化): 服务器发来证书 → 浏览器用内置的 CA 公钥验证书上的签名 → 签名有效 → 证明这证书真是 CA 盖的,里面的公钥真是这网站的 → 才敢用它。

四、TLS 1.2 完整握手(2 个 RTT)

下面是时序图。1 个 RTT = 一次一来一回。握手要让双方算出同一个会话密钥才能开聊。

          ┌─────────── RTT 1(谈判 + 服务器亮身份)──────────┐
Client ── ClientHello ──────────────────>  Server    // 我支持这些算法 + 随机数A
Client <── ServerHello ──────────────────   Server    // 选定算法 + 随机数B
       <── 证书(服务器公钥,CA 签名) ──   Server    // 先亮身份证
       <── ServerKeyExchange ─────────   Server    // DHE:额外发 DH 参数
       <── ServerHelloDone ───────────   Server
          ┌─────────── RTT 2(客户端交钥匙 + 收尾)──────────┐
Client ── ClientKeyExchange ───────────>  Server    // RSA:用公钥加密预主密钥
       ──                                   // DHE:发自己的 DH 公钥
Client ── ChangeCipherSpec ─────────>  Server
Client ── Finished(加密) ──────────>  Server
Client <── ChangeCipherSpec ─────────   Server
       <── Finished(加密) ───────────   Server
          // 至此双方用 随机数A + 随机数B + 预主密钥 算出同一个会话密钥
会话密钥怎么"凑"出来的? 双方各持三样东西——随机数 A(客户端)、随机数 B(服务器)、预主密钥。 前两个握手时明文互发(防重放),第三个靠密钥交换保密传(RSA 加密 或 DHE)。 三者喂进同一段 KDF → 双方算出完全相同的会话密钥。这段叫"密钥导出"。

五、为什么 TLS 1.2 必须要 2 个 RTT?

🤔 关键追问: 为什么不能把 RTT 2 的 ClientKeyExchange 合进 RTT 1 的 ClientHello 一起发?

答:客户端的密钥交换消息"卡在服务器先发的东西"上,没法提前发。

  • RSA 密钥交换: 客户端要用服务器的公钥加密预主密钥——而这把公钥在服务器证书里。 证书是 RTT 1 服务器才发过来的。客户端没收到证书前,根本不知道往哪加密。
  • DHE 密钥交换: 客户端要先拿到服务器的 DH 参数(ServerKeyExchange 里), 才能算出自己的 DH 公钥。这参数也是 RTT 1 服务器才发过来的。
一句话: 客户端的密钥交换素材 依赖服务器先发来的证书/DH 参数, 存在数据依赖 → 必须一来一回 → 多花一个 RTT。这是协议设计的天花板,不是网络慢。

六、TLS 1.3 怎么砍到 1 个 RTT?

💡 核心洞察:安全精简 和 握手提速 是同一件事。

第一步:大扫除。 TLS 1.3 把所有不安全的算法都删了——

  • 删 RSA 密钥交换(没有前向安全性,见第七节)
  • 删 CBC 模式(容易遭 padding oracle 攻击)
  • 删 SHA-1 / MD5(哈希可碰撞)
  • 只保留 (EC)DHE 做密钥交换 + AEAD 做加密。

第二步:算法空间变小 → 客户端能"预判"。

TLS 1.2(算法多)TLS 1.3(算法少)
支持 RSA / DHE / 各种组合…
客户端猜不到服务器会选哪个 →
不敢提前发密钥素材
(万一服务器选了 RSA,塞 DH 参数就白塞了) 		只剩 (EC)DHE 这一类 →
客户端几乎确定服务器会选 ECDHE →
直接把密钥素材(key_share)
塞进 ClientHello 一起发

第三步:数据依赖被解除 → 省 1 个 RTT。 客户端不再等服务器的证书/DH 参数, 第一发就把自己的 DH 公钥送出去。服务器收到,立刻能算出会话密钥,回包里把"证书 + Finished"全带回来。

          ┌─────────────── RTT 1(就这一个)───────────────┐
Client ── ClientHello ──────────────>  Server
       ── key_share(自己的 DH 公钥)   // 素材提前塞!关键
          // 服务器收到已能算出会话密钥
Client <── ServerHello ──────────────   Server
       <── {EncryptedExtensions} ──   // 后面全是加密的
       <── {Certificate} ──────────   // 证书也加密传
       <── {Finished} ─────────────   Server
Client ── {Finished} ──────────────>  Server
       ── 应用数据(可同发) ────>           // 握手完,马上传 HTTP
对比:TLS 1.2 要 2 RTT 才到第一个应用数据;TLS 1.3 只要 1 RTT。
省下来的那一来一回,在弱网(比如 200ms RTT 的移动网络)上 = 省 200ms 首字节。

七、前向安全性:为什么 RSA 被删

🔐 前向安全性(Forward Secrecy): 即使服务器长期私钥以后被泄露, 过去已经抓到的握手流量也无法被解密。
密钥交换私钥泄露后,历史流量会怎样?
RSA 密钥交换 预主密钥是用服务器公钥加密的。黑客如果之前抓了包,等私钥泄露 → 用私钥解出预主密钥 → 历史流量全部裸奔。
没有前向安全性 → 被 TLS 1.3 删掉。
(EC)DHE 每次握手都生成一对临时 DH 密钥,握手完就丢。 会话密钥只依赖这对临时密钥,跟服务器长期私钥无关。
黑客拿到长期私钥 → 解不了旧的 DH 临时私钥(已销毁) → 历史流量依然安全。有前向安全性。
关键:"前向"指的是"保护过去"。临时密钥是一次性的,用完即焚, 所以即便"现在的钥匙"被攻破,"过去的信"也烧不回来了。

八、0-RTT:第一个包就带数据(但有坑)

TLS 1.3 还有个可选加速:0-RTT 恢复。条件是你最近连过这个服务器。

机制: 第一次握手后,服务器发一个 Session Ticket(PSK) 给客户端。 下次重连时,客户端第一个包就带上 PSK + 应用数据——不等握手完成。 真正"零"往返开销
⚠️ 但 0-RTT 有重放(Replay)风险,不能随便用!
  • 攻击者可以截获这个 0-RTT 请求,原样重发给服务器。服务器分不清这是真请求还是重放。
  • 所以 0-RTT 只能用于幂等请求——比如 GET(读多少次都一样)。
  • 绝对不能用于会改状态的请求(POST /pay、POST /transfer…)。 否则一笔转账被重放 N 次。

十、面试速记口诀

HTTPS = HTTP + TLS,混合加密是灵魂。
非对称商量钥匙,对称开门干活; 慢的只用一次,快的干重活。

证书验身份,不加密。CA 是公证处,浏览器信的是预装根 CA。

1.2 花两轮,因为客户端要等服务器的证书/DH 参数;
1.3 砍成一轮,因为算法精简 → 客户端敢预判 → 素材提前塞。
安全精简和握手提速,是同一件事。

(EC)DHE = 临时钥匙 + 用完即焚 = 前向安全。 RSA 做不到,所以被删。

0-RTT 靠 PSK,首包带数据;但有重放风险,只许 GET。
