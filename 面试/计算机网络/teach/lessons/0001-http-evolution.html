计算机网络面试 · HTTP 三件套 ①

第 1 课：HTTP/1.1 → HTTP/2 → HTTP/3 演进

目标：这节课结束，你能按时间顺序讲清每一代治好了哪种队头阻塞、又留下了什么新坑。约 18 分钟。
一句话定位：HTTP 每一代都在治队头阻塞（Head-of-Line Blocking，HOL），只是治的层级不同—— 应用层 → TCP 层 → 彻底根治。
能讲清这条因果链，是面试里 HTTP 这块拿分的关键。

一、直觉类比（一个故事贯穿三代）

把TCP 连接想成超市的收银通道，把请求/响应想成顾客。三代 HTTP 就是这家超市收银区的三次改造：

① HTTP/1.1 —— 只有一个收银台，一人买一车
前面那位顾客买了一整购物车东西（= 一个大响应体正在传），你只买一瓶水（= 一个很小的请求）， 也得在后面干等他结完账。这就是「应用层队头阻塞」。
② HTTP/2 —— 收银台改成传送带，商品拆成贴编号的小盒子
每个顾客的商品不再一整车上货，而是被打包成一连串贴了编号（stream id）的小盒子， 所有顾客的盒子一起丢上传送带、交替发送。谁的盒子先到谁就先拼装，不用等别人。
这就是「多路复用」。但注意：传送带只有一条。
③ HTTP/3 —— 把单一传送带拆成一排独立快递通道
每个顾客走自己的独立通道。A 通道上有个盒子掉地上了（= 丢包）， 只影响 A 通道，B、C、D 通道照传不误。
这就是 QUIC：流与流之间互不拖累。

记住这个故事，下面每一节技术细节都能对应回这里。

二、HTTP/1.1：应用层队头阻塞

HTTP/1.1 默认每个 TCP 连接在同一时刻只能服务一个请求——前一个响应没传完，下一个请求就不能开始。这就是应用层队头阻塞：排在队头的请求一旦慢，后面全堵。

怎么硬扛的？

  • 浏览器对同域名开 6 条并发 TCP 连接。6 条线各跑一个请求，把堵车摊薄。这是治标：连接开多了，每个都要 TCP 握手 + TLS 握手，开销大，而且每条连接内部该堵还是堵。
  • keep-alive：让一条 TCP 连接可以连续发多个请求，免去重复握手。但它只是打补丁——这些请求仍然得一个一个串行，队头阻塞一点没少。
面试官爱追问：管道化（pipelining）为什么没救成？
HTTP/1.1 有个 pipeline 特性，允许「连发多个请求」。但它要求响应必须按请求顺序返回—— 第一个响应慢，后面的就算算好了也得排队等。队头阻塞没解决，还引入了新问题，所以现实中几乎没人开。

二、HTTP/2：二进制分帧 + 多路复用

HTTP/2 不再是纯文本协议，而是把每个请求/响应拆成一个个二进制帧（frame），每个帧带一个 stream id 标明它属于哪个流。多个流的帧在同一条 TCP 连接里交替传输，到了对端再按 id 重新拼装。

这就是多路复用（multiplexing）：一条 TCP 连接同时承载无数个并发请求，互不等待。

解决了什么：
  • 连接数 6 → 1。一个域名只用一条 TCP 连接，省掉了 5 次重复握手。
  • 应用层队头阻塞被治好：大请求和小请求的帧交替上链路，小请求不用再等大请求传完。
  • HPACK：头部压缩，重复的 Host、User-Agent 等只传一次索引，省带宽。
顺带一提：Server Push 已废弃。HTTP/2 曾允许服务器主动推送资源（如 CSS/JS），但实践中 客户端缓存难以配合、容易推多余内容，主流浏览器已移除支持。知道它存在过即可，别再当优点讲。

三、HTTP/2 的遗留坑：TCP 层队头阻塞

多路复用治好了应用层的队头阻塞，却把所有流塞进了同一条 TCP 连接——这埋下了新的雷：

TCP 层队头阻塞（TCP-layer HOL）：
TCP 的契约是「字节流必须按序交付给应用」。HTTP/2 的所有 stream 共用这一条 TCP， 一旦第 N 个字节丢了，TCP 即使已经收到了 N+1, N+2...， 也会扣住这些后续字节不交给上层，直到 N 重传成功。

于是：一个丢包，卡住整条连接里所有流——包括那些根本没丢包的流。多路复用越是把流量集中到一条连接， 这个放大效应就越明显。

类比回传送带：传送带卡了一下（丢包），所有顾客的盒子全停，因为传送带要求严格按顺序出货。

四、HTTP/3：换 QUIC，流独立可靠

既然坑出在 TCP 本身，HTTP/3 的解法很激进：不用 TCP 了，改用基于 UDP 的 QUIC 协议。

QUIC 的三把刀

  • 流独立可靠（核心）：QUIC 在一条连接里维护多个 stream，每个 stream 自己管自己的序号和重传。stream A 丢包，只重传 A 的数据，B、C 照常按序交付给应用。TCP 层队头阻塞被根治。
  • 握手 + 加密合并，省 RTT：QUIC 把「传输层握手」和「TLS 加密握手」揉在一起。首次连接 1 RTT 完成（TLS 1.3 over TCP 通常要 1 RTT + TCP 的 1 RTT = 2 RTT）；对曾连过的服务器还能 0-RTT 直接带数据发出去。
  • 连接迁移：连接的标识不再是「IP + 端口」，而是一个 Connection ID。你从 WiFi 切到 4G，IP 变了，连接不断，视频不会断流。
澄清最大误区（必考）：HTTP/3 用 UDP ≠ 不可靠。
原生 UDP 确实不管丢包——但 QUIC 在 UDP 之上自己实现了一套可靠传输（序号、确认、重传、拥塞控制）。 说白了：把 TCP 的可靠机制搬到应用层重做了一遍，但做成了「按流独立」，不再一刀切卡所有数据。
所以「HTTP/3 用 UDP 会不会丢数据」——不会，QUIC 保可靠。
面试加分点：首次访问要几个 RTT？（推导，别背结论）
从「发起连接」到「拿到首字节」，从第一个包开始数：
  • HTTP/2（TCP + TLS 1.2）：TCP 握手 1 RTT + TLS 1.2 握手 2 RTT + HTTP 请求/响应 1 RTT = 4 RTT。
  • HTTP/3（QUIC）：握手与 TLS 合并 1 RTT + HTTP 请求/响应 1 RTT = 2 RTT（0-RTT 模式甚至能 1 RTT 带数据返回）。
这就是为什么 QUIC 的握手合并对移动端弱网价值巨大。

五、三代对比小表格

版本 核心痛点 解法 遗留问题
HTTP/1.1 应用层队头阻塞：一个慢请求堵住同连接后续请求 浏览器对同域名开 6 条并发 TCP 连接硬扛；keep-alive 复用连接（打补丁，仍串行） 6 条仍不够；连接内串行；头部明文重复
HTTP/2 应用层 HOL 没根治干净 + 连接数浪费 二进制分帧 + 多路复用：一条 TCP 跑多个 stream，连接数 6→1；HPACK 头部压缩 TCP 层队头阻塞：一个丢包卡死整条连接所有流
HTTP/3 TCP 层队头阻塞（HTTP/2 的遗留坑） 换 QUIC（UDP）：流独立可靠；握手 + TLS 合并省 RTT；连接迁移 UDP 在部分企业防火墙/弱网被阻，实践中会 fall back 回 TCP
看这张表的正确姿势：每一行的「遗留问题」就是下一行要治的「核心痛点」。
因果链是连续的：1.1 的痛点催生 2 的解法，2 的解法又催生 3 的解法。面试时把这层递进关系讲出来，比罗列特性值钱得多。

七、面试速记口诀

1.1 应用层 HOL —— 一个慢请求堵住后续；浏览器多开 6 条 TCP 连接硬扛。

→ 2 多路复用治好了应用层 HOL，却因所有流共跑一条 TCP，引入了 TCP 层 HOL（一个丢包卡死全部流）。

→ 3 换 QUIC（UDP），流独立可靠，握手 + TLS 合并省 RTT，根治。

一句话版：每一代都在治队头阻塞，只是从「应用层」下探到「TCP 层」，最后换传输协议彻底根治。
